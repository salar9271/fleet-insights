# Fleet Insights — Senior ML Engineer Audit

Scope: full repository as of the current `main` (4 commits, HEAD `ccc3c70`). Read-only
audit — nothing in the repo was changed to produce this document. Claims below were
checked against the actual code, the actual data in `data/processed/` and
`data/driving_behavior_v2/`, and the actual committed artifacts in `models/` and
`reports/`, not just against the prose in the READMEs.

## Executive summary

This is an unusually honest project for a portfolio piece: it sets out to test
whether phone accelerometer/gyroscope windows can recover a 3-class driving-behavior
label via unsupervised clustering, gets a mediocre answer (ARI 0.12), and — instead
of hiding or reframing that — runs a second diagnostic (supervised RandomForest) to
figure out *why*, then documents the conclusion plainly. The train/test split is
session-disjoint and leak-free everywhere I checked, seeds are pinned, and the
clustering code goes out of its way to keep true labels out of every unsupervised
decision (scaling, k-selection, eps-selection, cluster naming). That discipline is
real and worth crediting.

But two things undercut the headline conclusion itself, not just its packaging:
the 16-feature set has at least one literally duplicated feature and a cluster of
four features correlated at r=0.79–0.94, which mechanically manufactures the
"single dominant intensity axis" the project reports as a finding; and every
statistical claim in the project (silhouette 0.373, ARI 0.12, macro-F1 0.49) is
computed over 180/152 *windows* that reduce to 3–4 *independent driving sessions* —
with no cross-validation across sessions to show the numbers are stable rather
than a description of these four specific drives. Separately, the API's startup
path re-fits the entire clustering pipeline from scratch to generate LLM-prompt
inputs, alongside loading a separately-persisted model for scoring — two models
that happen to agree today with nothing in the code guaranteeing they always will.

None of this is exotic to find — a candidate who ran their own diagnostic
(permutation importance) and their own correlation check would have caught the
duplicated feature. That combination — sound infrastructure, weak self-critique on
the feature-engineering layer that most directly explains the headline result —
is exactly what the findings below lay out.

## Findings by severity

### CRITICAL

**C1 — The "single intensity axis" finding is partly a multicollinearity artifact, not purely a discovery about the data.**

`jerk_std` and `jerk_rms` are **r = 1.000** correlated on the actual train windows
(verified directly against `data/processed/windows_train.parquet` — with
window-mean jerk ≈ 0, RMS and std of the same signal are numerically identical).
`acc_mag_mean`, `acc_mag_std`, `acc_mag_max`, and `acc_mag_p95` are pairwise
correlated **0.79–0.94**. That's 5 of the 16 features encoding essentially one
quantity five times, computed in `src/features.py:106-121`. `accX_std` and
`accX_max_abs` add a sixth near-duplicate at r=0.857.

KMeans and the StandardScaler that feeds it treat every feature as an
independent, equally-weighted axis in Euclidean space (`src/clustering.py:36-39,
96-103`). Six near-identical features pointing the same direction don't just add
noise — they get **six votes** toward that direction versus one vote for anything
orthogonal to it. That this produces a clustering dominated by "one intensity
axis" (README: PC1 = 48.6% of variance) is the *expected mechanical consequence*
of the feature set, not solely a fact about driving behavior. The project's own
downstream diagnostic makes this visible after the fact and never closes the
loop: `reports/rf_permutation_importance.csv` shows 11 of the 16 features have
permutation importance at or below noise level (std larger than the mean), and
the 5 that matter are exactly the redundant acc_mag/jerk cluster plus
`spectral_energy_ratio`. That table was generated by
`scripts/diagnostics.py` *after* clustering, and nothing feeds it back — no
de-duplicated or PCA-whitened re-clustering was attempted, despite the
diagnostic pointing directly at the fix.

- **Concrete risk:** the README's "Key results" state the clustering finding as if
  it were a property of the driving data ("the algorithm has separated
  higher-motion driving windows from calmer ones"). Some of that separation is a
  property of the feature matrix's geometry — duplicate a feature enough times
  and *any* clustering algorithm will find that axis first, regardless of what's
  actually happening physically.
- **Interview question:** "You have `jerk_std` and `jerk_rms` in a 16-feature
  list — did you check they're not the same number twice? What happens to your
  k-selection and cluster profile if you drop the correlated duplicates and
  re-run?" This is answerable in five minutes with the data already in the repo,
  and not having run it is the finding.

**C2 — Effective sample size is 3–4 independent sessions, not 180/152 windows; no cross-validation exists to show any reported number is stable.**

Verified directly: `windows_train.parquet` has 180 rows drawn from exactly
**4** `session_id` values (`train-0..3`, one class artificially split into two
sessions by a mid-recording pause per `docs/data_selection.md`); `windows_test.parquet`
has 152 rows from **3** sessions. Every headline number in the project —
silhouette 0.373 at k=2, ARI 0.1077/0.1197 (train/test), RandomForest macro-F1
0.4900 — is a point estimate computed once, on one fixed train/test session
assignment, with **zero** resampling, bootstrap, or leave-one-session-out
cross-validation anywhere in the codebase. With only 4 candidate train sessions,
leave-one-session-out CV was straightforward to run and would have shown whether
"k=2 wins" and "ARI≈0.12" are stable across which session plays the role of
held-out data, or an artifact of this one particular assignment (e.g., is the
result the same if `train-2`, the smallest session at 26 windows, is swapped for
the current test session instead?).

The project's docs *do* disclose the single-session-per-class limitation
(`docs/data_selection.md`, README Limitations) — credit for that. But the
numbers themselves are still reported to four significant figures throughout
(0.1197, 0.4900) with no accompanying uncertainty, which reads as far more
statistical confidence than 3–4 sessions can support. Windows within a session
are also not independent even though they don't literally overlap (see H2
below) — they're 20-sample slices of one continuous, autocorrelated drive.

- **Concrete risk:** any of these numbers could shift meaningfully with a
  different session-holdout assignment, and there is no way to tell from this
  repo whether they would. A stakeholder reading "ARI = 0.12" as a stable,
  reproducible property of the phenomenon (rather than of these four specific
  drives) is being misled by the precision of the presentation, even though the
  prose caveats are honest.
- **Interview question:** "If I gave you a fifth recorded session for the SLOW
  class, how confident are you that k=2 would still win the silhouette sweep?
  What would you have to run to answer that, and why didn't you run it here?"

### HIGH

**H1 — API startup silently re-fits the entire clustering pipeline; nothing guarantees the model used for scoring matches the model used for the LLM narrative.**

`src/api.py:68-84` (`lifespan`): the scaler and KMeans model used for every
`/analyse` prediction are loaded from the persisted artifacts
(`models/scaler.joblib`, `models/kmeans.joblib`, produced once by
`scripts/run_clustering.py`). But two lines later, the same function calls
`run_clustering()` **again**, from scratch — re-running the full KMeans sweep
(k=2..6) *and* the DBSCAN eps sweep — purely to obtain `cluster_profile` and
`test_ari` for the LLM prompt (`state["cluster_profile"]`, `state["test_ari"]`,
lines 78-80). This is two independently-derived models where only one is
persisted to disk and loaded; the other is rebuilt on every process start from
whatever happens to currently be in `data/processed/`.

Today, with a fixed `RANDOM_STATE=42` and the current parquet files, these
happen to agree. But nothing in the code enforces that: there is no hash, no
version stamp, no test asserting `state["kmeans"].cluster_centers_` matches a
fresh fit, and no check that `data/processed/windows_train.parquet` is the same
data that produced `models/kmeans.joblib`. If someone reruns
`scripts/build_features.py` with a code change (or a refreshed Kaggle download)
without also rerunning `scripts/run_clustering.py`, the API will silently start
scoring requests with a **stale** KMeans model while narrating results using a
**freshly-fit** cluster profile from different data — a silent train/serve skew
with no error, no log line, no test to catch it. Separately, refitting a 5-way
KMeans sweep plus a DBSCAN eps sweep on every server boot is pure waste: the
numbers it needs (`profile`, `test_ari`) are already sitting in
`reports/cluster_profile.csv`, just not loaded from there.

- **Concrete risk:** silent skew between what a request is scored with and what
  the LLM brief describes, triggerable by the ordinary workflow of "regenerate
  features, forget to also regenerate the model" — an easy mistake with no
  guardrail.
- **Interview question:** "Your API loads a saved model but then also refits the
  whole pipeline at startup for the LLM prompt — walk me through what happens if
  those two ever disagree. How would you know?"

**H2 — No overlap between windows (confirmed), but that is not the same as independence, and the "16 features, n=180" framing throughout obscures that.**

Directly confirmed in `src/features.py:135-140`:
`n_windows = len(session_df) // window_length`, tumbling windows via
`iloc[start:end]` with `start = w*window_length` — genuinely non-overlapping,
no window-level leakage. This part is done correctly and is worth crediting
explicitly, since overlapping-window leakage is one of the most common mistakes
in this exact kind of pipeline.

The residual issue is weaker but real: adjacent windows within the same session
still share driving context (same stretch of road, same maneuver spanning a
window boundary, same driver on the same day). Non-overlap rules out the
*worst* leakage mode (sample reuse across train/test), but it doesn't make the
180 train windows statistically independent draws — see C2. This is a distinct
point from C2 (which is about cross-validation and sample size); this one is
specifically about whether "180 windows" should be read as "180 observations"
anywhere in the reporting. It shouldn't, and the README's "Key results" section
doesn't flag that distinction where the numbers are first stated.

**H3 — Hardcoded, unverified LLM model ID; failures degrade silently rather than being surfaced.**

`src/genai_report.py:17`: `MODEL = "claude-sonnet-4-6"`. I cannot confirm this
against a current, valid Anthropic model identifier from within this audit — it
does not match any model family I have on record. Whether or not it's
currently valid is a fast thing to check and fix; the actual finding is the
failure mode if it (or any future model ID) is wrong: `generate_report()` will
raise `GenAIReportError` on the resulting `APIStatusError`
(`src/genai_report.py:128-129`), which `src/api.py:183-189` catches and turns
into a *soft* `notice` field on an otherwise-200 response, and
`scripts/generate_report.py:78-82` turns into a `sys.exit(1)` in the script
path. In the API path specifically, a broken model ID produces no error, no
log entry, and no alert — just a quietly-degraded response that a caller has to
notice by reading the `notice` field. That's a reasonable *design* for
resilience (the numeric results should still be served), but there's no
matching observability to catch a persistently-broken LLM path in production.

- **Interview question:** "If `claude-sonnet-4-6` stopped being a valid model
  tomorrow, how would you find out? Walk me through what happens to a live
  deployment, end to end." The honest answer today is: nobody would notice
  until someone reads a `notice` field in a JSON response.

### MEDIUM

**M1 — No test suite, no CI.** Nothing in the repo asserts the API's own
documented contract (e.g., that malformed CSVs actually return 422 with the
described messages, that `use_llm=false` actually skips the LLM call, that the
loaded scaler/model shapes match the current feature set). This means H1's
failure mode (skewed model vs. profile) has no safety net, and any future
refactor of `src/features.py` or `src/clustering.py` could silently change the
16-feature contract the saved `models/*.joblib` were fit against, with nothing
to catch it before it reaches an endpoint.

**M2 — Reproducibility gap between the documented Quickstart and the full set of committed reports/artifacts.** The README's Quickstart
(`README.md:139-153`) runs `build_features.py` → `run_clustering.py` →
`generate_report.py` → `run_api.sh`. It never runs `scripts/diagnostics.py` —
that script is mentioned only in the pipeline diagram
(`README.md:30`), never as a step to actually run. Consequence, confirmed by
checking what each script writes: following the Quickstart exactly does **not**
regenerate `models/random_forest.joblib`, `models/kmeans_k3.joblib`,
`reports/cluster_profile_k3.csv`, `reports/feature_separation_by_class.csv`,
`reports/rf_permutation_importance.csv`, or any of the four PNGs in
`reports/figures/` (those need `make_figures.py`, itself undocumented as a
required step — mentioned only as an optional aside). A fresh clone reproduces
the core clustering artifacts (`models/scaler.joblib`, `models/kmeans.joblib`,
`reports/cluster_profile.csv`) but **not** the RandomForest comparison, the
k=3 comparison, or a single figure, without knowing to run two scripts the
Quickstart never names. `models/*.joblib` are committed directly to git as
binary blobs (2.2MB for `random_forest.joblib` alone) with no versioning tying
them to the code/data revision that produced them — they were committed once,
in the single large commit discussed in L1 below, and nothing re-derives or
checks them since.

**M3 — Silhouette-based k-selection is methodologically appropriate but not stress-tested.** Using train-only silhouette to pick k without ever
touching true labels (`src/clustering.py:57-60`) is the right unsupervised
procedure and is implemented cleanly. But it's evaluated once, on one fixed
`random_state=42`, over a feature space already known (C1) to be dominated by
a redundant intensity axis — which biases silhouette toward whatever k best
splits that one axis. No seed-sensitivity check, no stability check under
bootstrap resampling of the 180 windows. Given how cheap this would be to run
(the k-sweep already exists in `kmeans_sweep()`), its absence is a missed easy
win, not a fundamental flaw in the choice of silhouette itself.

**M4 — LLM output isn't validated beyond key presence; the "don't invent caveats" instruction is enforced by prompt only.**
`src/genai_report.py:19` (`REQUIRED_KEYS`) checks that the five expected keys
exist in the model's JSON response — it does not check types (e.g., that
`evidence`/`caveats` are actually arrays, not strings) or that `caveats`
matches the fixed `KNOWN_LIMITATIONS` list the prompt hands the model
(`genai_report.py:73-75`, "do not invent others, and do not omit these"). The
prompt design here is genuinely good — grounding the model in pre-computed
facts is the right pattern — but there is no code-side guardrail if the model
ever drifts from those instructions (adds a plausible-sounding fourth caveat,
returns a string where an array is expected). Low probability given how
constrained the prompt is, but a single unenforced assumption away from
shipping a fabricated caveat in a "driving-safety brief."

**M5 — API has no auth, rate limiting, request-size limit, CORS policy, or structured logging.** Expected and acceptable for a portfolio
demo running locally; flagged here only because the code comments and
docstrings use production-adjacent language ("production readiness" is in
scope for this audit). As shipped, `POST /analyse` accepts an arbitrarily large
multipart upload from anyone with network access, does CPU-bound work
(windowing, scaling, KMeans predict, an outbound LLM call) synchronously inside
an `async def` handler with no offloading, and logs nothing on failure beyond
what uvicorn prints by default. None of this needs fixing for the project's
current purpose; it does need fixing before "FastAPI service" becomes "thing I
put behind a real fleet's telematics pipeline," and a hiring manager evaluating
for a production-facing ML engineering role will look for the candidate to
know the difference explicitly rather than have it go unmentioned.

### LOW

**L1 — Git history shows no incremental engineering process.** `git log --stat`
shows 4 commits total. The entire implementation — `src/`, `scripts/`,
`models/*.joblib`, all of `reports/` including figures — lands in a single
commit (`a81ec40`, "docs: project README with results, figures, and API
usage"), 34 files and ~2,200 lines at once. The only other substantive commits
are two later doc-only tweaks. There is no commit history showing the actual
sequence of decisions this audit found well-reasoned in the docs (e.g.,
choosing `driving_behavior_v2` over `sensor_raw.csv`, picking the 0.2–0.8 Hz
spectral band, discovering the low ARI and designing the RandomForest
diagnostic in response). None of that reasoning is visible as *process* in git,
only as a finished narrative in prose — which is a strictly weaker signal in
any review that looks at commit history for evidence of how someone actually
works.

**L2 — Gyroscope features are treated inconsistently with accelerometer features.** `acc_mag` (`src/features.py:92`) gives the accelerometer
features a mount-orientation-robust magnitude norm. No equivalent
`gyro_mag` exists; all three gyro features are raw per-axis standard
deviations (`gyroX_std`, `gyroY_std`, `gyroZ_std`), which are sensitive to
how the phone happens to be mounted/oriented in the vehicle — an
uncontrolled variable in this dataset. This is consistent with the project's
own finding that gyro features separate the classes weakly
(`reports/clustering_findings.md`: "Gyro features show weak separation for
all three classes") and with the permutation-importance table showing all
three gyro features at noise level. A mount-invariant summary (total
rotational rate, analogous to `acc_mag`) was an available, cheap thing to try
and wasn't.

**L3 — "Jerk" features are not in physical units.** `src/features.py:99`:
`jerk = np.diff(acc_mag)` — a raw sample-to-sample difference, not divided by
the sampling interval, so it isn't jerk in m/s³, just a first difference in
the same units as acceleration. In this dataset it's a low-severity nitpick
because per-session `session_fs_hz` is nearly constant across all sessions
(1.851–1.855 Hz, verified directly), so the missing normalization doesn't
distort comparisons here — but the feature is mislabeled, and the code would
silently produce incomparable "jerk" values if reused on data with variable
sampling rate.

**L4 — Minor docs/code mismatch on sampling rate.** `docs/data_selection.md`
states the estimated sampling rate is "~1.7 Hz" and uses that figure to justify
the Nyquist-based choice of spectral band. The actual per-session
`session_fs_hz` values computed by the pipeline and stored in the parquet files
are **~1.85 Hz** (verified directly) — 1.7 Hz turns out to be the whole-file
average that includes the large inter-session gaps, not the per-session figure
the code actually uses for windowing. This doesn't change the conclusion (0.925
Hz Nyquist at 1.85 Hz is still comfortably above the 0.2–0.8 Hz band), but it's
a factual inconsistency between the documented reasoning and what the code
computes.

## Coverage notes (by topic requested)

**Data leakage — scaler, session boundaries, window overlap, train/test split, models-before-API.**
Scaler fitting is clean: `fit_scaler()` is called with `train_df` only, in every
call site (`run_clustering()`, `diagnostics.py`, and implicitly at serving time
via the persisted `models/scaler.joblib`) — verified no code path ever calls
`.fit()` on test or upload data. Session boundaries are enforced correctly:
`segment_sessions()` cuts at both large timestamp gaps *and* class changes
(`src/features.py:47-67`), and windows are built per-session so they can't span
a boundary. Window overlap: none, confirmed (H2) — tumbling, not sliding,
windows. Train/test split: it's the pre-existing Kaggle file split, and I
independently verified zero timestamp overlap and zero exact-duplicate sensor
rows between `train_motion_data.csv` and `test_motion_data.csv` — the project's
own disjointness claim in `docs/data_selection.md` holds up. The
"models fit before the API loads them" concern is real, but not in the sense of
classic data leakage — it's the H1 architecture issue: the *serving* model is a
properly-persisted, train-only-fit artifact; the problem is a second,
independently-refit copy exists in the same process for a different purpose,
with nothing tying the two together.

**Feature engineering — 16 features: justified, redundant, missing something obvious?**
Redundant: yes, materially (C1) — one exact duplicate pair, one four-feature
cluster at r=0.79–0.94. Justified: partially — `accY_rate_below_neg3` /
`accY_rate_above_pos3` (hard-braking/hard-acceleration event rates at a 3 m/s²
threshold) and `spectral_energy_ratio_0.2_0.8hz` are genuinely distinct,
well-reasoned signals not captured by the magnitude/std family, and the 3 m/s²
threshold is a defensible, roughly industry-standard hard-braking cutoff.
Missing: a mount-invariant gyro magnitude (L2); any per-axis directional bias
feature beyond `accY_mean` (no `accX_mean`, though a symmetric lateral signal
may genuinely average near zero and be low-value); any interaction/ratio
feature (e.g., simultaneous high lateral + high longitudinal acceleration, which
would flag "braking while turning" more precisely than either axis alone). The
feature set was never revisited after the permutation-importance diagnostic
revealed which of the 16 actually carry signal (C1).

**Evaluation — silhouette k-selection, ARI as the external metric, RandomForest fairness, is n=180 enough.**
Silhouette selection: methodologically clean (never touches labels) but
untested for stability (M3) and confounded by C1. ARI: the correct choice for
comparing an unsupervised partition to ground-truth labels — chance-corrected,
permutation-invariant, doesn't require matching cluster/class counts. Well
applied; NMI/V-measure alongside it would have made the "k=2 gets homogeneity
right but completeness wrong" story even more precise, but that's a nice-to-have,
not a gap. RandomForest comparison: fairly set up — same features, genuinely
held-out session-disjoint test set, macro-F1 (correct metric for imbalanced
3-class) benchmarked against a real majority-class baseline rather than raw
accuracy. Whether n=180 is enough: no, not for the strength of claim implied by
reporting numbers to four significant figures with no cross-validation (C2) —
though it is enough to support the narrower claim the docs actually make in
their Limitations sections ("this describes these recorded sessions," not "this
generalizes").

**API design and production readiness.** Clean separation of concerns, sensible
422 error handling with descriptive messages for malformed uploads
(`src/api.py:94-130`), and a well-designed graceful-degradation path for the
LLM (`use_llm=false`, missing key, and API failure all converge on the same
numeric-only response shape). Undercut by H1 (silent train/serve skew risk) and
M5 (no auth/rate-limit/logging) for anything beyond local/demo use. `scripts/run_api.sh`
runs uvicorn with `--reload` — fine for a demo script, wrong flag to leave in
anything resembling a deployment command.

**Does the LLM add real value or is it decoration?** Modest but real value,
correctly scoped. It's not doing analysis — every fact it's allowed to state is
handed to it as pre-computed numbers (`build_prompt()`,
`src/genai_report.py:44-95`), and the actual "is this cluster higher-risk"
determination is deterministic code (`name_cluster()`,
`src/clustering.py:106-113`) that runs with or without the LLM. What the LLM
adds is translation: turning a z-score table into fluent, unit-aware,
operationally-framed prose ("say m/s², never g") for a non-technical fleet
audience — comparing the real generated brief (`reports/fleet_brief.json`) to
the stored mock example (`reports/fleet_brief_example.json`) shows consistent,
well-grounded output that doesn't hallucinate beyond the numbers it's given.
That's a legitimate use of an LLM as a report-writing layer, not a
decision-making one, and it's honestly labeled as such throughout. The real
gaps are reliability-related (H3, M4), not value-related.

**Reproducibility — seeds, pinned versions, does a fresh clone reproduce the numbers.**
`RANDOM_STATE=42` is consistently threaded through KMeans, RandomForest,
permutation importance, and the PCA figure. `requirements.txt` pins exact
versions (`==`) throughout, no floating ranges. `.env` is correctly gitignored
and not committed (verified). Where this falls short: M2 — a fresh clone
following the documented Quickstart reproduces the core clustering artifacts
but not the RandomForest/k=3 diagnostics or any figure, because
`scripts/diagnostics.py` is never listed as a step to run.

## What this looks like to a hiring manager

**Working in the project's favor:**
- The core failure mode this kind of take-home/portfolio project usually has —
  shuffled row-level train/test splits that leak temporal/session correlation —
  is explicitly avoided, correctly, with the reasoning written down
  (`docs/data_selection.md`). That's a specific, checkable signal of statistical
  maturity, not just a claim.
- When the headline unsupervised result came back weak (ARI 0.12), the project
  didn't reframe or bury it — it designed a second, bounded diagnostic
  (supervised RandomForest as a "is the signal even there" check) and reported
  a conclusion that's more nuanced and more defensible than either "clustering
  works" or "clustering failed." That instinct — investigate a disappointing
  number instead of narrating around it — is exactly what a senior/staff
  interview loop is trying to find.
- The system is end-to-end (ingestion → features → model → API → LLM narrative
  → docs), not a notebook, and the code is legible and consistently organized.

**Working against it:**
- The single-commit history (L1) removes the strongest evidence a reviewer
  normally has for *how* someone works — debugging, false starts, iteration on
  the k-selection or feature set. Everything here reads as a finished
  narrative; nothing reads as process. An interviewer who asks "walk me through
  how this came together" is asking a question this git history can't answer.
- The most sophisticated-sounding parts of the write-up (the ARI diagnostic,
  the k=3 comparison) sit on top of a feature set with an exact-duplicate pair
  and a four-feature multicollinear cluster that nothing in the project's own
  process caught (C1) — despite the project running the exact diagnostic
  (permutation importance) that would have surfaced it. That's the kind of gap
  a technical interviewer will find in the first five minutes of looking at the
  feature table, and it's a harder miss to explain than the honestly-disclosed
  small-sample limitation, precisely because the tools to catch it were already
  in the repo and unused.
- No tests, no CI, and a real (if currently dormant) architecture bug in the
  one production-shaped component (H1) will read as "research-quality code,
  not yet engineering-quality" to anyone hiring for a role where the model
  serving path matters as much as the modeling.

Net: this is a candidate who clearly understands *statistical* rigor (leakage,
label-blind unsupervised procedure, honest external validation) noticeably
better than they've yet applied *engineering* rigor (tests, commit hygiene,
serving-path consistency) or a second pass of *self-critique on their own
feature set* using diagnostics they already know how to run.
